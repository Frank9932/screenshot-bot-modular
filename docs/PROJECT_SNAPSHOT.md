## One-line description

A WeChat Official Account webhook bot that, when a user sends a channel number or
photo, captures a screenshot of a corresponding browser tab (a login-gated building
-management dashboard, driven headlessly via Chrome DevTools Protocol), watermarks it,
and sends it back — with per-user archival storage, a config-driven set of channels
(including hidden "backup" and passcode-gated "private" channels), optional
per-channel watermark customization via chat commands, and an optional guided
equipment-selection flow, deployed to Windows hosts via Ansible/WinRM behind a
Cloudflare tunnel.

## Project Overview

- **Origin**: refactor of an earlier monolith, [screenshot-bot](https://github.com/Frank9932/screenshot-bot),
  into capability modules. This repo explicitly excludes wx-cli, desktop WeChat
  polling/UI automation, and managing a *production* tunnel (bring-your-own stable
  ingress; this repo only provides throwaway/dev tunnel convenience tooling).
- **Primary real-world target**: Schneider Electric EcoStruxure Building Operation
  WebStation, a login-gated internal dashboard at a fixed IP (`10.121.0.14`), config
  target name `webstation-test`. Multiple WeChat "channels" (text digits) each map to
  one already-authenticated tab of this one site.
- **Deployment**: Windows 11 hosts (`win11-bot-01/02/03`) via Ansible over WinRM, one
  shared Chrome process per host, cloudflared for ingress (quick tunnel for testing,
  permanent named-tunnel Windows service for production).
- **Not a generic product**: config (`browser_targets.targets`, watermark fields,
  login selectors) is written for this one specific site/deployment, though the code
  itself doesn't hardcode it.

## Architecture

Capability-module architecture with one orchestration layer, enforced by convention
(not tooling) — a module doesn't reach into another module's internals; only
`workflow/` composes multiple capability APIs.

```text
scripts/ (entrypoints, demos, ops tools)
  -> workflow/  (orchestration: message_router decides, WeChatImageReplyWorkflow executes)
       -> browser/     (Chrome/CDP capture + watermark)
       -> wechat/      (WeChat Official Account protocol/API)
       -> runtime/      (dedupe, logging, clock, generated images)
       -> screenshot_store/  (persist already-captured bytes)

wechat/webhook_server.py -> injected message_processor.handle(...) only (no capture logic)
```

Within `workflow/`, there's a second-order split worth calling out: `message_router.py`
is a **pure function** (`route_message(...)`) that takes message + sender state and
returns a decision dict, with zero I/O — no WeChat API, no browser, no filesystem.
`wechat_image_reply.py`'s `WeChatImageReplyWorkflow` is a thin executor of those
decisions (sends replies, calls `browser.capture`, persists tracker state). This split
is recent (this branch) and is what makes `python -m screenshot_bot.workflow.message_router`
runnable as a standalone interactive REPL for debugging routing logic with no live bot.

## Module Map

| Module | Responsibility | Depends on |
|---|---|---|
| `browser/` | Own the shared Chrome process; named-tab CDP client; login/keep-alive/refresh for login-gated sites; watermark rendering; per-channel watermark overrides; equipment-graphic navigation | `screenshot_store`, Pillow |
| `wechat/` | WeChat Official Account HTTP protocol: signature verify, webhook ACK/dedupe/async dispatch, access-token-cached API calls (image/text send, media download, menu create/get), XML parsing | `runtime` |
| `workflow/` | The only orchestrator. Routes messages (`message_router.py`, pure), executes decisions (`wechat_image_reply.py`), tap-menu building/translation (`menu.py`), watermark chat-command grammar (`watermark_commands.py`), per-user channel/private-unlock state (`user_team_tracker.py`), equipment select-flow (`equipment_catalog.py`, `equipment_prompts.py`, `equipment_selection_tracker.py`), plain-language reply text (`help_text.py`) | `browser`, `wechat`, `runtime`, `screenshot_store` |
| `runtime/` | Business-logic-free utilities: TTL message dedupe, JSONL event logging, timestamps, tagged console logging, generated latency/error PNGs | stdlib, Pillow |
| `screenshot_store/` | Persist already-captured PNG bytes under a caller-chosen key path; returns `ScreenshotRecord` | stdlib only |
| `device-agent-mvp/` | **Unrelated, disconnected prototype** — see "Known Issues" below | OpenAI/OpenRouter SDK |

Removed this branch: `desktop/` (virtual-desktop screenshot capability) — deleted
entirely as dead code (`virtual_desktop.enabled` was always `false` in every config
that shipped).

## Public Interfaces

Each capability module has a `README.md` under `src/screenshot_bot/<module>/` that is
treated as the contract: public API, input, output, dependencies, run method, test
method, example. These are unusually thorough and are the closest thing this project
has to an interface spec — read them before changing a module's call signature. As of
this snapshot they are current for `browser/`, `wechat/`, `workflow/`, `runtime/`.
**`screenshot_store/README.md` is stale** — see "Known Issues".

Key stable entrypoints:
- `screenshot_bot.browser.BrowserScreenshotService(config_path).capture(team_id, ...)`
- `screenshot_bot.wechat.webhook_server.WeChatWebhookServer(..., message_processor)`
- `screenshot_bot.workflow.build_wechat_official_server(config_path, host, port, path)`
- `screenshot_bot.workflow.message_router.route_message(...)` — pure decision function
- `scripts/run_wechat_official_webhook.py` — process entrypoint (CLI args: `--config-path`, `--host`, `--port`, `--path`, `--ready-file`, `--warmup-teams`)
- `scripts/Bot.ps1` — unified ops CLI (`status`, `webhook {start,stop,restart,logs,watch}`, `browser {restart,warmup}`, `tunnel {start,stop,permanent-install}`, `menu {set,get}`, `all {kill,restart}`)

Interfaces still actively changing: `message_router.route_message`'s signature has
grown `equipment_*` parameters recently and will likely keep growing if the
equipment-catalog flow is extended; `screenshot_store` key conventions have changed
shape twice (`tab_{tab}` → `channel_{team_id}` → `{user_id}/channel_{team_id}/{original,watermarked}`)
without the module's own README following each rename.

## Technical Debt

- Duplicated near-identical `browser_targets.targets` entries in `config.example.json`
  (8 near-copies differing only in `tab`) — intentional per the "team-per-tab" pattern,
  but there's no config-level shorthand for "N tabs of the same target," so every new
  channel is a full block copy-paste (documented as intentional in `browser/README.md`,
  not flagged as debt there, but worth knowing if this list grows further).

  debuggable" incident fix) does not protect against **cross-process** concurrent

  silent swallow) but a real non-elevated manual restart retest was never confirmed
