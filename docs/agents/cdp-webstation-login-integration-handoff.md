## 1. What this conversation accomplished

Built, in order:
1. A minimal, dependency-free (stdlib-only) CDP multi-tab screenshot service: launch one Chrome instance, add named tabs, screenshot any tab without stealing foreground focus, list tabs.
2. Extended it for a real internal login-gated site (`https://10.121.0.14/` — Schneider Electric EcoStruxure Building Operation WebStation) at the user's request: capped tab count, login automation, and discovered/worked around the site's real operational constraints (single-active-session-per-account, SPA bootstrap timing, self-signed cert).
3. Reverse-engineered the site's own frontend JS to find its real session-keepalive mechanism, then replicated it (`keep_alive`) rather than inventing an arbitrary ping.
4. Added a second, distinct background loop (`refresh` / auto page reload) to address content staleness, which is a different problem from session keepalive.
5. Wired all of the above into the *production* WeChat-facing capture path (`BrowserScreenshotService` / `BrowserProfileManager`), not just the standalone demo scripts — config-driven, credentials via env vars, with a real integration bug found and fixed along the way (duplicate-tab-on-restart).
6. Documented the credentials setup end-to-end (local + Ansible-deployed) and verified the documented `warm_up()` verification flow actually works and actually surfaces the exact error message documented.

Every claim below that says "verified" was actually run against the real site (`10.121.0.14`, account `Huawei`) during this conversation, not just written speculatively.

## 2. What's actually in the code (as this conversation left it)

**New file** `src/screenshot_bot/browser/cdp_multi_tab_service.py` (stdlib-only, built on the pre-existing `DevToolsWebSocket`/`http_json` in `devtools_client.py`):
- `launch_chrome()`, `wait_for_port()`, `resolve_chrome_path()` — process/port helpers. `launch_chrome` resolves `user_data_dir` to an absolute path (found and fixed a real bug: Chrome silently fails to open its debug port if given a relative path).
- `CdpMultiTabService`: `add_tab`, `has_tab`, `list_tabs`, `screenshot` (uses `Page.captureScreenshot` with `fromSurface: true` — this is what allows capturing a backgrounded/non-focused tab at all).
- `login(name, username, password, ...)` — fills `#txtUserID`/`#txtPassWord` via the native `<input>` value setter + `input`/`change` events (needed for framework-controlled inputs), clicks `#login`. Hard-gates on the page reaching a `loginPageLoaded` body class before touching the DOM (the SPA tears down and re-renders the login form after its own bootstrap; touching it too early either hits elements about to be discarded or a submit button with no listener attached yet, and the site's own load time is genuinely variable — seen 1s to 30+s under load). Detects "already authenticated" (redirected off `login.html`) and returns fast instead of waiting for a form that will never appear.
- `keep_alive(name, ...)` — sends the exact request shape the site's own frontend uses to keep its session alive (see §"reverse-engineering" below), via `GetServersInfo` (path-independent, unlike the site's own `PeekObjects` which needs a valid object path our tabs don't have).
- `start_keep_alive`/`stop_keep_alive` — background daemon thread, one per tab name, mirrors the site's own 60s interval. **As this conversation left it, a failed ping is only logged (`print`), never recovered/retried actively** — the later `browser-session-recovery-handoff.md` session added active recovery on top of this; that is not this conversation's work.
- `refresh(name, ...)` / `start_auto_refresh`/`stop_auto_refresh` — `Page.reload()` on a timer, per tab (unlike keep_alive, this is NOT shared across tabs of the same site — each tab has its own DOM/subscriptions).
- `adopt_tab(name, url_prefix)` — matches an already-open tab by URL prefix and registers it under a name instead of opening a duplicate. Built specifically to fix a real bug found during integration testing (see §5 decisions/bugs below).

**Modified** `src/screenshot_bot/browser/profile_manager.py`:
- `BrowserProfileManager.ensure_tab()` now: creates or *adopts* the target's tab, then (only the first time this process sees that tab name — tracked so a failed attempt is retried, not permanently skipped) calls a new `_apply_login()` which reads credentials from env vars named by the target's config, calls `login()`, and conditionally starts `keep_alive`/`refresh` loops per the target's config.
- `ignore_certificate_errors` config passthrough to `launch_chrome` (needed for the self-signed cert on `10.121.0.14`).
- **Note:** by the time this conversation ended, an external edit had already landed on top of this file adding a `tab_count`/multi-tab-per-target concept (`ensure_tab(..., tab_index=...)`, `app_url`, a `warm_up()` method on `BrowserScreenshotService`) — this conversation used and verified that machinery (see §1 point 6) but did not author the multi-tab-per-target feature itself. ## 4. Decisions that were made, then reversed

- **Tab topology for "5 tabs, keep them logged in."** First attempt: point all 5 tabs at `login.html` and call `login()` on each independently. This *failed* — the site enforces one active login per account and rejected the 2nd–5th attempts with "a user is already logged on to another tab." **Reversed to:** tab 0 logs in on `login.html`; tabs 1–4 navigate directly to the app root URL and passively inherit the shared cookie (all tabs in one Chrome process share one cookie jar). This is the pattern that actually works and is what `run_cdp_webstation_demo.py` and the config-driven `login` block both implement.
- **"Keep the login alive" via persistent Chrome profile.** Initial assumption: a persistent `user_data_dir` would keep the session alive across a full Chrome restart. **Disproven by testing**: the site's session cookie is session-only (no `Max-Age`/`Expires`); it is cleared by the browser on close regardless of profile persistence. This is the *server's* cookie policy, not something fixable client-side. Corrected in all docs/docstrings: "keep the login alive" means keep the Chrome *process* running, not rely on the profile directory surviving a restart.
- **Login-readiness gate.** First implementation waited for `body.classList` to stop containing `"loading"` before interacting with the form. **Found insufficient**: the SPA tears its initial static-HTML form down and re-renders its *own* form after that point; the real signal is `body.classList.contains('loginPageLoaded')`. The `"loading"`-based gate was also initially a soft wait (proceeded to click even on timeout) — changed to a hard gate that raises, because clicking a not-yet-wired-up submit button reliably wedged the page (real bug, reproduced and fixed).
- **"Already authenticated" fast-path detection.** First version checked `location.href` doesn't contain `"login.html"`. **Found a real race**: right after `add_tab()`, the URL briefly reads `"about:blank"`, which also doesn't contain `"login.html"` — this caused every tab after the first to be wrongly fast-pathed as "already authenticated" without ever actually submitting credentials. Fixed by explicitly excluding `"about:blank"`.
- **`keep_alive`'s target command.** The site's own frontend uses `PeekObjects` for its keepalive ping, but that requires a valid object-tree path our tabs never navigate to (it would silently no-op). Switched to `GetServersInfo` — same authenticated-POST mechanism, no path required.
- **Tab-tracking across process restarts.** Discovered mid-integration-testing: `has_tab()` state is only in-process memory. A second, independent process pointed at the same already-running Chrome had no idea a tab already existed, so it created a *duplicate* tab and duplicate login attempt — which the site then rejected (single-session-per-account, see above). Fixed by adding `adopt_tab()`, called before `add_tab()` in `ensure_tab()`. Verified: a second process adopted the existing authenticated tab in <1s with no duplicate created.
- One transient failure during integration testing (a 30s login timeout) was initially unclear whether it was a code bug or environmental. **Root-caused to system resource contention**: ~12 stray `chrome.exe` processes had accumulated on the dev machine from repeated earlier test runs. Resolved by killing them, not by a code change. Worth remembering if similar flakiness recurs — check for zombie Chrome processes before assuming a logic bug.

## 5. Risks that still exist

1. **This conversation's `cdp_multi_tab_service.py`/`profile_manager.py` are not the current state of those files.** See the warning at the top. Anything below about "current behavior" should be re-verified against the live file, not trusted from this doc alone.
2. **`keep_alive` failures were never actively recovered by this conversation's code** — only logged. (A later session added recovery; not reconciled with this conversation's original design, per that session's own handoff doc, which itself flags an unresolved race between its recovery path and a third-party tab-locking mechanism.)
3. **`adopt_tab` matches by URL-origin prefix only.** If two different logical targets ever point at the same origin, adoption could grab the wrong one. Not exercised — only one real login-gated target exists in config today.
4. **No automated test coverage.** Everything was verified live against a real, network-dependent internal device (`10.121.0.14`). That device's reachability is environment-dependent — it worked from this sandbox but is not guaranteed elsewhere.
5. **Real test credentials (`Huawei`/`Huawei@1234`) were used in plaintext in shell commands throughout this conversation** (env vars only — never written to a tracked file), but they were typed directly in terminal commands and appear in this conversation's transcript. Not rotated. Confirm with the user/ops whether this is an acceptable long-term test account or whether a dedicated service account should be provisioned before any real production reliance.
6. **`max_tabs` is a global cap across the whole shared Chrome process, not per-target.** With one login-gated target now configured for 5 tabs plus three 1-tab targets (8 tabs total), there's headroom under the cap value seen in config, but this is easy to blow past silently (generic `RuntimeError: tab limit reached`) if more targets/tabs are added later without revisiting this number.
7. **Login timeout (`timeout_seconds=30` default in `login()`) is a single fixed budget** covering both the "wait for page ready" step and (separately) the "wait for post-submit redirect" step; under heavy load this conversation observed real, legitimate page-bootstrap times approaching 30s. No retry/backoff exists inside `login()` itself — only the outer `_apply_login`-not-cached-on-failure mechanism allows a *later, separate* `capture()`/`warm_up()` call to retry.
8. **No supervision of the shared Chrome process.** If it crashes, `has_tab()` would still report tabs as "known" (in-memory dict), but the underlying CDP calls would then fail in a way this conversation never explicitly tested (vs. the tested "process restarted, Chrome still alive" scenario, which `adopt_tab` handles).

- **The production entry points are `BrowserScreenshotService.capture(team_id, tab=0, ...)` and `.warm_up()`**, not the standalone `CdpMultiTabService` directly — those are what the WeChat webhook actually calls. `warm_up()` is the recommended way to validate credentials/login before relying on a target in production or a test run; it returns per-target `{"tabs": [...], "errors": [...]}` rather than raising, so one bad target doesn't block others.
- **Credentials**: `WEBSTATION_USERNAME`/`WEBSTATION_PASSWORD`, set via `secrets.local.ps1` (local) or `ansible/files/secrets.local.ps1` (deployed) — never in tracked config. Not validated at server startup (unlike the WeChat secrets); only checked lazily the first time a login-gated target's tab is created, and a missing var raises a clear, specific `RuntimeError` scoped to that one target.
- **The site's real operational constraints, confirmed by testing, that any future change must respect**: (a) only one active login session per account — never attempt a second concurrent `login()` submission while another tab already holds a valid session for the same account, only navigate additional tabs to a non-login URL; (b) the session cookie is session-only — don't design anything that assumes it survives a Chrome restart; (c) the SPA's real bootstrap/login-readiness signal is the `loginPageLoaded` body class, not `"loading"` clearing; (d) `about:blank` is a real, observed transient state immediately after tab creation and must not be misread as a meaningful URL.
